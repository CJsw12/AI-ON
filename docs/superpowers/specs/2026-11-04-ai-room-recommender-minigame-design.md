# AI 강의실 추천 미니게임 설계안

- 상태: 검토용 초안. 이 문서는 설계 제안이며 구현 승인 전에는 코드와 에셋을 변경하지 않는다.
- 작성일: 2026-11-04
- 대상: AI-ON 컴퓨터공학과의 수업 프로젝트와 미니게임

## 1. 의도

개발자가 시연 영상을 봤을 때 AI가 장식 문구가 아니라 실제 입력 데이터로 학습하고, 처음 보는 사례를 예측하며, 그 판단의 근거와 한계를 드러낸다는 점을 짧은 시간 안에 이해하게 한다. 게임 플레이 자체도 데이터와 모델을 다루는 작은 엔지니어링 과제가 되게 한다.

AI-ON은 학과별 첫 학기 이야기를 진행하는 Unity 비주얼 노벨이다. 컴퓨터공학과 이야기는 팀이 가상의 강의실 시간표를 이용해 빈 강의실 찾기 프로그램을 만들고, 실제 학교 데이터는 쓰지 않기로 한다. 마지막에는 추천 기능을 실험용으로 미뤄 둔다. 이번 미니게임은 이 추천 기능의 프로토타입을 만들고 평가하는 장면으로 그 흐름을 이어간다.

## 2. 현재 프로젝트와 제약

- Unity 6000.3.23f1, 단일 씬, 1280×900 고정 IMGUI 화면.
- 미니게임은 `MiniGame` 기반 C# 클래스이며 `MiniGameKind`와 `MiniGames.Create`에 등록한다.
- 컴퓨터공학과에는 카드 복습, 반복문 버그 사냥, 커피 주문 미니게임이 있다. 새 게임은 이 학과의 기존 미니게임 하나를 교체하거나 이야기 슬롯을 조정해야 한다. 전체 공통 미니게임을 바꾸지 않는다.
- `MiniGames.Create`는 경험자 여부를 미니게임에 전달하므로, 경험자/입문자 플레이 차이를 구현할 수 있다.
- `Packages/manifest.json`에는 ML 추론 패키지가 없다. 설계 기본안은 외부 패키지나 API 없이 C#으로 실행되는 설명 가능한 소형 모델이다.
- 실제 시간표, 학생 기록, 개인정보는 사용하지 않는다. 게임 내 고정 합성 데이터만 사용한다.

## 3. 게임 개요

**가제:** 빈 강의실 AI 추천 연구실

**상황:** 팀 프로젝트 사용자가 인원, 필요한 장비, 선호 환경을 입력한다. 시스템은 시간표상 이용할 수 있고 하드웨어 요구도 충족하는 방을 먼저 추린 다음, 과거의 가상 피드백에서 학습한 모델로 적합한 방의 순위를 매긴다.

**플레이 목표:** 학습 데이터의 오류와 모델 복잡도를 살펴보고, 검증 성능을 유지하면서 새 팀 요청에 좋은 강의실을 추천한다. 추천을 그대로 받아들이거나, 근거를 보고 직접 수정할 수 있다.

**예상 플레이 시간:** 약 90~150초. 시연 영상에서는 핵심 흐름을 45~60초로 편집한다.

### 한 판의 흐름

1. **요청 확인** — 새 팀 요청과 후보 강의실 세 곳을 받는다.
2. **데이터 점검** — 가상 과거 기록 중 모델이 참고할 사례를 살펴본다. 일부 예시는 피드백 라벨이 잘못되어 있다.
3. **모델 설정 및 학습** — 규제 강도가 다른 랭킹 모델을 학습하고 학습 점수와 검증 점수 차이를 비교한다.
4. **추천 평가** — 새 요청에 대해 모델이 후보 방을 순위화한다. 확률, 판단 경로, 제약 조건 통과 여부를 보여준다.
5. **사람의 피드백** — 추천을 수락하거나 더 나은 방을 고른다. 두 방의 선호 관계를 새 학습 사례로 추가하고 모델을 즉시 갱신한다.
6. **재학습 및 요약** — 모델 갱신 후 결과를 다시 보여준다. 결과 화면에는 추천 품질, 검증 지표, 사람이 고친 사례 수를 표시한다.

점수는 추천 결과의 적합도, 검증 데이터에서의 일반화, 제약 조건 준수, 불확실한 예측을 사람에게 넘긴 판단을 함께 반영한다. 학습 데이터에 과하게 맞춘 모델이 무조건 높은 점수를 얻지 않도록 한다.

## 4. 모델과 데이터 설계

### 4.1 문제를 AI에 맡길 범위

시간표상 예약 여부, 방의 최대 수용 인원, 필수 장비 보유 여부는 명확한 규칙으로 확인한다. 이 조건은 일반 코드로 필터링한다. AI는 그 필터를 통과한 후보 사이에서 사용자의 선호에 더 잘 맞는 방을 순위화한다.

이 분리를 통해 “규칙으로 정확히 풀 수 있는 일을 굳이 AI로 포장한다”는 인상을 줄이고, 학습 모델이 필요한 부분을 명시한다.

### 4.2 특징과 학습 라벨

목표는 이진 분류가 아니라 **후보 방의 선호 순위 학습**이다. 한 학습 사례는 `(요청, 방 A, 방 B, 사용자가 더 선호한 방)`으로 저장한다. 사용자가 두 후보를 비교한 선호 관계를 학습하기 때문에, 게임의 추천 목표와 라벨의 의미가 일치한다.

- 요청 특징: 팀 인원, 조용한 공간 선호, 필요한 장비, 이동 거리 허용 범위.
- 방 특징: 좌석 수, 소음 수준, 장비, 건물 위치, 예약 가능 여부.
- 요청-방 특징 벡터: 수용 인원 적합도, 장비 충족률, 조용함 일치도, 이동 거리 비용, 예약 가능 여부.
- 예약 여부·수용 한계·필수 장비는 모델 입력만으로 해결하지 않고 규칙 필터에서 하드 제약으로 처리한다.
- 합성 데이터: 고정 시드로 생성하는 약 120~200개의 서로 다른 요청과 각 요청의 후보 비교 기록. 같은 요청에서 만들어진 쌍이 학습과 검증 세트에 나뉘지 않도록 **요청 ID 단위로 분할**한다.
- 과거 선호에는 일부 불일치 사례가 포함된다. 플레이어는 요청과 방 조건을 비교해 문제 사례를 찾아 피드백한다. 민감 속성은 생성하거나 사용하지 않는다.

합성 데이터는 시연과 재현을 위한 게임 데이터다. 실제 학교의 점유율 또는 실제 학생 선호를 대표한다고 주장하지 않는다.

### 4.3 1차 모델 제안: Pairwise Logistic Ranking

후보 쌍의 특징 차이를 이용하는 **쌍대 로지스틱 랭킹**을 C#으로 구현한다. 신경망 프레임워크나 서버 없이도 모델 학습, 추론, 피드백에 따른 갱신을 모두 게임 내부에서 보여줄 수 있다.

1. 각 후보 방을 요청 특징과 결합해 벡터 `x`로 만든다.
2. 현재 가중치 `w`로 방의 적합 점수 `s = w · x`를 계산한다.
3. 학습 사례 `(A, B, A 선호)`에서 `sigmoid(w · (xA − xB))`를 A 선호 확률로 예측한다.
4. 예측과 라벨의 차이를 로지스틱 손실로 계산하고, L2 정규화를 포함한 확률적 경사 하강법(SGD)으로 `w`를 갱신한다.
5. 새 요청에서는 하드 제약 통과 방을 점수 순서로 정렬한다. 가중치와 특징별 기여도를 설명 경로로 보여준다.
6. 사용자가 추천을 수정하면 새 선호 쌍을 학습 세트에 추가하고 소수의 SGD 업데이트를 즉시 수행한다.

초보자에게는 데이터 예시와 재학습 결과를 중심으로 보여준다. 경험자는 학습률, L2 정규화 강도, 반복 횟수 중 제한된 선택지를 조절해 과적합과 업데이트 안정성의 차이를 확인한다. 값은 안전한 범위로 고정한다.

**모델 신뢰 처리:** 후보 1위와 2위 점수 차이가 작으면 “선호가 확실하지 않음”을 표시하고 사람의 선택을 요청한다. UI의 확률은 모델의 비교 점수에서 계산한 추정치라고 명시한다. 별도 보정 절차 없이 보정된 확률인 것처럼 부르지 않는다.

**재현성:** 데이터 버전, 분할 seed, 초기 가중치 seed, 학습 설정을 기록한다. 같은 입력과 seed에서 동일한 학습·예측 결과가 나와 녹화 경로를 재현할 수 있다.

개발자가 검토하기 쉽게 특징 생성, 하드 제약 필터, 학습, 추론, 평가를 분리한다. 비용 함수와 gradient는 작은 수치 예제로 검산하고, 런타임에서는 배열 할당과 학습 반복을 제한한다.

### 4.4 평가 화면

기술 지표는 게임 화면을 압도하지 않게 ‘모델 상세’ 패널에 단계적으로 보여준다.

- 학습/검증 요청 수, 데이터셋 버전, 분할 seed.
- 고정 검증 요청에서의 Pairwise Accuracy와 NDCG@3. 학습 점수와 검증 점수의 차이가 크면 일반화 저하를 표시한다.
- 규칙 기반 기준선과 모델의 검증 성능을 나란히 비교하고, 특징을 하나씩 뺀 ablation 결과를 상세 패널에서 선택적으로 확인한다.
- 요청별 후보 순위, 점수 차, 특징별 기여도, 미충족 하드 제약.
- ‘확신 낮음’ 상태와 사람에게 판단을 넘긴 횟수.
- 사용자 피드백 전후의 가중치 변화 및 후보 순위 변화.
- 게임 점수는 가상 데이터에 대한 미니게임 판정이며, 실제 캠퍼스 추천 성능으로 표현하지 않는다.

## 5. 난이도와 플레이 감각

### 입문자

- 데이터 예시와 특징의 뜻을 짧게 알려준다.
- 추천을 고르면 예측 근거를 쉬운 표현으로 설명한다.
- 모델 설정은 ‘안정적으로 학습’과 ‘피드백에 빠르게 반응’ 두 선택지로 단순화한다.
- 지표 대신 선호 순위가 맞은 요청과 어긋난 요청을 카드로 보여준다.

### 경험자

- 정규화 강도, 학습률, 업데이트 횟수의 제한된 설정을 조정한다.
- 학습·검증 Pairwise Accuracy와 NDCG@3, 기준선 대비 성능을 확인한다.
- 가중치와 특징 기여도, 피드백 전후 순위, 학습/검증 성능 격차를 살펴보고 일반화가 나빠진 모델을 찾아야 한다.

두 모드 모두 같은 새 요청을 추천하고, 같은 기본 목표를 수행한다. 경험자 모드는 기술 정보를 추가하고 데이터/모델 판단의 자유도를 높인다.

### 실패 피드백

- 잘못된 추천은 왜 어긋났는지 특징과 제약에 연결해서 알려준다.
- 모델이 확신이 낮을 때는 자동 실패로 처리하지 않고 사용자에게 선택을 넘긴다.
- 검증 점수 저하는 학습 데이터에 과도하게 맞춘 징후로 설명한다.
- 학습 확인용 예제와 검증 예제를 섞어 보여주지 않는다.

## 6. 이야기 연결 제안

컴퓨터공학과 이야기의 마지막 발표 전날에 추천 기능을 테스트하는 장면으로 연결한다. 팀은 기능을 시연할 수 있지만, 모델이 확신하지 못하는 사례와 학습 데이터의 한계를 발견한다. 다음 날 발표에서는 검증한 강의실 검색 기능을 기본으로 보여주고, AI 추천은 실험 기능이라고 설명한다.

이 결말은 기능을 무리하게 완성품으로 포장하지 않고, 모델 평가와 한계를 이해하는 개발자다운 판단을 드러낸다. 엄격한 교수는 데이터 분리와 재현성, 유쾌한 교수는 사용자가 결과를 수정할 수 있는 상호작용을 칭찬하는 식으로 기존 두 교수의 성격을 살린다.

통합 위치는 기존 컴퓨터공학과의 세 미니게임 중 하나를 대체하는 안을 우선 검토한다. 특히 발표 전날 커피 주문 미니게임 슬롯을 바꾸려면 대사와 장면도 AI 기능 점검에 맞게 같이 수정해야 한다. 슬롯 수와 엔딩 구조는 유지한다. 커피 미니게임은 다른 학과에서 계속 사용할 수 있다.

## 7. 시연 영상 구성안 (45~60초)

| 구간 | 화면 | 전달할 내용 |
| --- | --- | --- |
| 0–5초 | 팀 요청과 세 후보 강의실 | 해결할 문제가 한눈에 들어온다 |
| 5–13초 | 데이터셋 카드, 오류 라벨 표시 | 어떤 데이터를 학습하는지 알 수 있다 |
| 13–22초 | 빠른 업데이트/강한 정규화 설정의 학습·검증 점수 비교 | 학습 안정성과 일반화의 trade-off를 보여준다 |
| 22–32초 | 새 팀 요청, 후보 순위와 결정 경로 | 모델이 본 적 없는 입력에 예측하고 근거를 제시한다 |
| 32–42초 | 플레이어가 추천을 수정하고 피드백 저장 | 사람의 감독과 학습 데이터 갱신을 보여준다 |
| 42–52초 | 재학습 후 확률/검증 결과 변화 | 피드백이 실제 모델 결과에 반영된다 |
| 52–60초 | 게임 속 데모 발표 장면 | AI의 효용과 한계를 이해한 프로젝트임을 마무리한다 |

시연 빌드에는 고정 시드 ‘골든 패스’를 제공한다. 영상 녹화 시 난수 결과, 성공 기준, 추천 순위가 바뀌지 않게 하고, 모든 조작은 일반 게임 화면 안에서 수행한다.

## 9. 성공 기준

- 네트워크 연결 없이 학습, 검증, 예측과 피드백 재학습까지 시연된다.
- 새 요청 입력 → 예측 → 근거 확인 → 사용자 피드백 → 모델 갱신의 흐름이 1분 안에 보인다.
- 시연 경로에서 학습·검증 Pairwise Accuracy와 NDCG@3를 기준선과 비교할 수 있다.
- 하드 제약을 위반하는 방은 AI 점수가 높아도 추천되지 않는다.
- 낮은 신뢰도 예측은 자동 확정하지 않고 사람에게 넘긴다.
- 같은 데이터 버전과 시드로 동일 결과를 재현할 수 있다.
- 결과와 문구가 AI 성능을 실제보다 과장하지 않고 합성 데이터 한계를 명시한다.
- 초보/경험자 두 모드 모두 조작만으로 한 판을 마칠 수 있고, 경험자 모드에서 기술 지표를 설명할 수 있다.

## 10. 범위 밖

- 생성형 대화, 음성 인식, 웹캠 감정 분석.
- 실제 학생·시간표 정보 수집 또는 서버 분석.
- 전 학과에 AI 기능을 확장하는 일.
- AI가 교수 대사를 자유 생성하는 일.
- 미니게임을 여러 개 추가하거나 프로젝트 전체를 ML 플랫폼으로 전환하는 일.

## 11. 구현자가 해결할 항목

이 설계 승인 후 구현 계획에서 아래를 확정한다.

1. 실제 교체 대상 슬롯과 챕터 대사 변경량. 현재 1차 안은 발표 전날 슬롯의 커피 게임을 AI 추천 게임으로 교체하되, 커피 주문 언급을 장면에 맞게 다시 쓴다.
2. 데이터셋 크기, 요청별 그룹 분할, 선호 라벨 생성기와 불일치 비율.
3. pairwise logistic loss/gradient, L2 정규화, SGD 설정, metric 계산, 낮은 점수 차 임계값.
4. 경험자/입문자 UI 차이와 화면 레이아웃.
5. 미니게임 전용 클래스와 `MiniGameKind` 등록 및 연습 메뉴 설명.
6. 알고리즘 단위 검증, 고정 시드 영상용 실행 경로, Unity 빌드 검증.

## 12. 자체 설계 검토

- AI가 맡는 일과 규칙 코드가 맡는 일을 분리했다. 시간표의 빈 시간 확인을 학습 모델에 맡기지 않는다.
- 같은 요청에서 파생된 후보 쌍은 한쪽 데이터 분할에만 두어 학습/검증 간 데이터 누수를 막는다.
- 낮은 신뢰도 처리, 고정 시드, 모델 근거를 포함해 영상 재현성과 실제 게임의 사용자 통제를 다룬다.
- 데이터 편향을 이야기할 때 개인정보나 민감 속성 대신 합성 선호 기록의 라벨 오류를 사용한다.
- 기술 패널이 초보자 플레이를 막지 않도록 설명 모드와 상세 모드를 나눈다.

이 설계가 승인되기 전에는 구현을 시작하지 않는다.
