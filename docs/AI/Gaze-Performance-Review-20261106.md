# AI-ON 아이트래킹 개선 조사 — 2026-11-06

현재 코드와 공개 논문·작성자 저장소를 비교한 조사다. 게임 코드·패키지·인증·장치 설정은 변경하지 않았다. 기준은 AI-ON HEAD `8ee9aa6`와 현재 미커밋 시선 코드다. 다른 도구의 작업은 보존했다.

## 판단

현재 구조를 유지하면서 **시각 정렬 → 클릭 학습 검증 → 필터 지연 조정 → 품질 판정 → 모델 비교** 순서로 개선하는 편이 구현 부담 대비 유리하다. 새 라이브러리만 교체해서 개선된다고 판단할 근거는 아직 없다. 아래 우선순위는 코드 분석에 따른 권고이며 실제 정확도 개선율은 측정하지 않았다.

## 확인한 현재 방식

- 로컬 UnitEye 패키지 1.1.0, MediaPipe 0.16.3, Unity Inference Engine 2.6.1.
- 웹캠: EyeMU+ResNet34 복합 모델. 고정점 9개 → 12초 8자 따라보기 → 학습에서 제외한 검증점 3개. 고정점 정착 .6초/수집 .9초, 따라보기 예고 1초, 총 명목 약31초.
- 웹캠 준비 화면은 UnitEye 기본 보정을 생략할 수 있고 GazeMapper에서 화면에 맞춘다. 일반 테스트 경로는 기존 UnitEye 보정 위에 화면 맞춤을 적용할 수 있다.
- ResNet 방향은 `GazeOnScreenPlane`에서 머리 위치·거리와 결합한다. 따라서 머리 위치 보정이 전혀 없다고 보고 전체를 새로 구현할 필요는 없다.
- GazeMapper는 축별 특징 선택, 표준화 릿지, leave-one-out+프레임 흔들림으로 모델 선택, 복잡한 모델 선택 억제를 사용한다. 회귀 강도는 고정 .005다.
- 클릭 학습: 클릭 전 .05~.45초, 최소3표본, 60px 안정성, 1.5초간 마우스 최대 변위40px 이상, 예측-클릭250px 이내 조건. 최근30개, 개당 .35 가중치. 마우스 이동 검사는 이미 들어 있다.
- UnitEye가 이미 One Euro 필터를 적용하고, 그 결과를 입력받은 게임 쪽에서 다시 One Euro+30px 고정 반경을 적용한다(웹캠). iPhone 고정 반경18px.
- iPhone은 VTube Studio Wi-Fi/USB 경로와 별도 보정 키를 유지한다. 새 iPhone 앱 교체는 웹캠 경로 개선과 별도 과제다.

## 1. 우선 적용: 수집 시각을 카메라 촬영 시각에 맞추기

위치: `Assets/Scripts/GameController.WebcamFit.cs:59–67,171`, `Packages/de.uniulm.uniteye/Scripts/Runtime/HomulerGaze.cs:146,654`.

현재 따라보기 표본은 `Time.unscaledTime`(게임에서 결과를 받은 시각)에 기록하고 목표점은 거기서 고정 .12초를 뺀 위치로 지정한다. 여기에는 카메라·추론 지연이 빠져 있다. UnitEye에는 이미 같은 Unity 시계의 `CaptureTimestamp`, `MeasuredLatencySeconds`가 있다. CaptureTimestamp는 코드에서 관찰 가능한 촬영 시각 근사치이며 센서 하드웨어 타임스탬프와 동일하다고 보장되지는 않는다. 화면의 지연 표시에만 쓰지 말고 학습 목표 정렬에 이용할 수 있다.

- 학습 표본은 `CaptureTimestamp`와 묶는다. 촬영 시각과 Unity 표시 시각의 시계/갱신 경로를 확인한다.
- 목표점의 표시 이력도 보존하고, 촬영 시각에서 사용자의 추적 반응 지연을 뺀 위치에 보간한다. 처리 지연과 사람의 반응 지연은 구분한다.
- .12초는 초기값으로 두되 개인별 지연 후보는 연속 시간 블록으로 분리해 평가한다. 같은 궤적의 인접 표본을 학습/검증으로 무작위 분리하면 지나치게 좋은 수치가 나올 수 있다.
- 입력인 `gazeTracker.gazeLocation`은 이미 필터링된 위치다. 현재 시각의 머리/방향 특징과 섞으면 특징끼리도 위상이 다르다. 보정에는 필터 전의 동기화된 특징을 쓰고 화면 출력에서만 필터링하는 경로를 비교한다. 기존 보정을 무조건 끄기보다 먼저 동일 조건 A/B로 확인한다.
- `HomulerGaze`에 이미 주시 이벤트·추적 표본의 시간 정렬 코드가 있으므로 관련 부분을 참고하고 중복 처리기를 추가하지 않는다.

현재 8자 궤적을 그대로 계산한 합성 예: 처리 지연이 추가로150ms인데 무시하면 학습 목표 위치가 평균40.7px, 최대61.4px 차이 난다. 100ms는 평균27.2px, 250ms는 평균67.9px. 이는 **목표 라벨의 시간 오정렬 계산**이며 실제 추적 오차나 개선율이 아니다.

근거: [Saxena 등의 연구/분석 코드](https://github.com/ShreshthSaxena/Eye_Tracking_Analysis)는 고정점·따라보기 조합을 연구하지만 현재의 9점+12초, .12초 상수를 보증하지는 않는다. [GazeFollower의 실제 설정 코드](https://github.com/GanchengZhu/GazeFollower/blob/main/gazefollower/misc/DefaultConfig.py)도 따라보기의 카메라/파이프라인 지연을 별도 설정으로 둔다.

## 2. 우선 적용: 클릭 학습의 정답 오염과 회귀 방지

위치: `GameController.ClickCalibration.cs:30–55`, `GazeMapper.cs:188–212`.

현재 이동량·안정성 검사는 유용하다. 다만 안정적으로 다른 곳을 보면서 버튼을 누르는 행동도 통과할 수 있다. `AddClick`은 새 모델을 바로 적용하며 기존 검증점 오차를 다시 검사하거나 모델을 되돌리지 않는다. `x.Error/y.Error`는 기존 값을 복사하고 `CheckPixels`도 유지하므로 학습 후 정확도가 변해도 표시 값은 옛 측정이다.

권고:

1. 전역 MouseDown을 바로 학습하지 않고 **실제로 처리된 명확한 UI 선택**에만 연결한다. 선택지 선택·의도적인 보정 클릭을 우선하고 대사 넘기기, 빈 배경, 드래그, 게임 도중 클릭은 제외한다. 버튼 중심을 실제 시선의 정답이라고 단정하지 않는다.
2. press/release를 함께 보고 드래그를 제외한다. 클릭 전 시간 창도 촬영 시각 기준으로 정렬한다.
3. 한 영역 클릭이 누적되어 모델 전체를 지배하지 않도록 화면 구역별 표본 상한/최소 분산을 둔다. 현재30개×.35=10.5개 보정점 무게이므로 고정점9개와 비교하면 가벼운 영향만은 아니다. 실제 따라보기 추가점까지 포함한 영향은 별도 측정해야 한다.
4. 새 모델은 후보로 계산하고, 따로 남긴 기준점/검증 세션에서 악화되면 적용하지 않는다. 실시간 독립 정답이 없으므로 과거 검증 데이터만으로 현재 자세에서의 개선이 증명되지는 않는다. 일정 횟수 후 짧은 확인점으로 보완한다.
5. 학습 중 정확도 수치는 '초기 검증'과 '최근 재검증'을 구분한다. 저장 보정을 불러와 오프셋만 바꾸는 경로도 같은 정책으로 확인한다.

근거: [Tri-Cam §3.4.2](https://arxiv.org/html/2409.19554v1)는 앱 맥락·press/release 시간·공간 분포를 검사하며 **게임/동영상 클릭은 시선과 정렬되지 않는 경우가 많아 수집 대상에서 제외**한다. 현재 코드의 마우스 이동량40px 검사는 이 논문에서 검증한 조건과 동일하지 않다. Tri-Cam의 카메라3대 결과도 이 프로젝트 단일 웹캠의 기대 성능으로 가져오면 안 된다.

순수 함수 합성 실험: 정확한 선형9점 데이터에 중앙을 보고120/1000 화면폭 오른쪽을 클릭했다는 잘못된 정답을30개 주면, 모두 수락되고 원래9점 평균 오차가2.38→82.72px로 증가했다. 입력값은250px 허용 범위 안이다. **실제31초 보정 전체나 UI 게이트를 재현한 결과가 아니고, 회귀 함수의 잘못된 정답 수용 영향만 확인한 실험**이다.

## 3. 우선 적용: 필터를 겹쳐 쓰는 효과와 고정 반경 분리

위치: `GameController.WebcamFit.cs:16,117,179`, `GazeMapper.cs:416–438`, UnitEye `HomulerGaze.cs:717`.

웹캠의30px fixation hold는 노이즈를 줄이는 대신 시선을 조금 옮겨도 포인터가 움직이지 않고, 이동 후에도 반경만큼 뒤처질 수 있다. 실제 함수를30Hz로 실행해20px 이동을10초 유지했을 때 출력은0px였다. 이는 현재 설계의 데드존 효과이며 예측 모델의 실패와 구분해야 한다.

- 동일한 재생 데이터로 UnitEye 필터만 / 게임 필터만 / 현재 이중 필터를 비교한다.
- 점 위치 추정과 게임 판정을 분리한다. 교수 얼굴 영역 판정에는 기존 히스테리시스를 활용하고, 시선 좌표 자체를30px 붙잡는 방식은 작게 줄이거나 제거하는 후보를 둔다.
- One Euro의 minCutoff/beta는 고정 주시 흔들림과 빠른 이동 지연을 따로 측정해 조정한다. 지금 수치를 임의로 바꾸고 개선됐다고 결론내리지 않는다.

근거: [One Euro 저자 설명과 구현](https://gery.casiez.net/1euro/)은 낮은 속도의 흔들림을 minCutoff로 먼저 조정한 다음 빠른 움직임의 지연을 beta로 조정하도록 안내한다. 이미 설치되어 있으므로 새 필터 패키지는 필요 없다.

## 4. 판정 신뢰도와 검증을 보강

- 현재 확인점3개의 중앙값 특징에 대한 평균 위치 오차만으로는 모서리, 순간 흔들림, 자세 변경 성능을 알기 어렵다. 훈련에 쓰지 않은 확인점9개에서 **프레임 단위 중앙/P95 오차, 유효 표본율, 지연, 눈맞춤 오탐/누락**을 함께 기록한다.
- `TryCompleteEyeContactPreparation`은 fitted/calibrated 여부만 확인하므로 높은 오차의 보정도 완료 후 바로 스토리로 들어간다. 확인 결과를 보여 주고 재시도/진행을 고르게 하는 후보가 있다. 얼굴 크기와 실제 허용 오탐 수준으로 기준을 정해야 한다.
- UnitEye에는 이미 `HasGazeModelConfidence`, `GazeModelConfidence`, provider의 `BinocularIrisDisagreement`가 있다. 이 신호를 시선 보정 표본·클릭 학습에서 활용할 수 있다. 값은 세션 상대 신뢰도이며 '80% 정확도' 확률로 해석하면 안 된다. 본인 세션에서 warmup과 임계값 측정이 필요하다.
- 추적 불량은 '교수를 안 봄'과 구분해 눈맞춤/이탈 감점 타이머를 정지하는 쪽으로 설계한다. 기존 fresh sample/눈감김 검사를 유지하고 저품질 표본에 대한 동작을 추가 검증한다.
- 웹캠의 머리 위치 기반 화면 투영은 이미 있으나, 물리적 화면/카메라 배치가 정확하다는 보장은 없다. 중앙 자세와 좌우/거리 변화의 독립 검증을 한다. iPhone은 `UsePosition=false`를 켜는 것만으로 해결되지 않는다. 머리가 움직이는 보정 데이터와 Wi-Fi/USB별 좌표·단위 확인이 먼저다.

관련 공개 구현: [Falch & Lohan 2024 논문](https://www.frontiersin.org/journals/robotics-and-ai/articles/10.3389/frobt.2024.1369566/full), [작성자 코드](https://github.com/FalchLucas/WebCamGazeEstimation). 이 프로젝트가 이미 일부 아이디어를 사용하므로 전체 Python 프로그램을 또 붙이기보다 좌표계·화면 기하 검증에 참고한다.

기존 파일 확인: EyeMUEmbedding 0.7MiB, ResNet34 81.5MiB, MobileOne4.7MiB, MobileNetV2 9.3MiB. 파일 크기는 FPS·정확도 측정치가 아니다. 작은 모델이 노트북에서 지연을 줄일 가능성은 있으나 기존 ResNet보다 정확하다고 단정하지 않는다. [원저자 모델 표](https://github.com/yakhyo/gaze-estimation)는 Gaze360 각도 오차를 보고하며, 보정된 PC 화면 픽셀 오차와 직접 비교할 수 없다.

## 실제 적용·검증 순서 제안

1. 동일인·같은 자세/조명/해상도로 현재 버전의 독립 검증 기록을 남긴다. 촬영 시각, 처리 시각, 실제 목표, 필터 전/후 예측, 유효성, 클릭 학습 적용 여부만 로컬 기록한다. 얼굴 영상 저장은 필요하지 않다.
2. 촬영 시각 정렬만 고쳐 같은 기록/시나리오로 비교한다.
3. UI 클릭 제한·후보 모델 회귀 검사·학습 끄기 스위치를 추가해 학습 전후를 비교한다.
4. 이중 필터/holdRadius 조합을 비교한다. 별잡기·눈빛 피하기는 반응 지연, 교수 눈맞춤은 오탐/누락을 우선 지표로 삼는다.
5. 현재 설치된 EyeMU / ResNet34 / MobileOne / 복합 모델을 각각 새로 보정해 비교한다. 게임 도중 모델을 자동으로 바꾸면 기존 보정이 무효이므로, 속도 측정과 모델 결정은 보정 전에 한다.
6. 위 수정 후에도 부족하면 WebEyeTrack 독립 데모를 평가하고 실제 이득이 확인됐을 때 Unity 연결을 진행한다.

최소 실기 조건: 여러 사람·안경 유무·밝기 조건, 각 조건3회 반복, 학습하지 않은 확인점, 중앙/좌우/거리 변화, 정지 목표와 이동 목표를 분리. 평균만 좋아지고 P95지연/눈맞춤 오탐이 나빠지는 변경은 채택하지 않는다. 다른 자세/표본에서 나온 두 오차를 개선율로 비교하지 않는다.
